# 【PRD】黑客松项目建联

> 文档状态：Draft
> 版本：v1.0
> 更新日期：2026-09-07
> 适用范围：黑客松项目
> 后续方向：抽象为平台 Project 的通用建联能力

## 1. 文档目的

本文定义黑客松项目建联功能的产品目标、用户流程、页面行为、权限、数据规则、邮件通知、异常处理、指标和技术改动，作为产品评审、交互设计、后端、前端和测试的共同依据。

本功能解决的问题是：用户在黑客松项目详情页发现感兴趣的项目后，可以直接向项目方提交联系申请；平台通过邮件提醒项目方，但不在邮件中泄露申请人的联系方式；项目方登录平台后在“连接记录”中处理申请；项目方接受后，双方在平台内解锁各自授权的联系方式。

本期只支持黑客松项目，不改变现有平台 `Project`、Talent Plaza 或现有 Talent `ConnectionRequest` 的领域语义。未来平台项目接入时，应复用本期沉淀的建联、联系方式加密、邮件通知和连接记录能力，而不是复制一套流程。

## 2. 背景与问题

当前用户发现黑客松项目后，没有直接联系项目方的闭环，通常需要：

1. 找到平台方人员。
2. 由平台方转述用户意向。
3. 平台方再向项目方确认是否愿意提供联系方式。
4. 双方在平台外建立联系。

这个流程有三个主要问题：

- 用户操作成本高，联系意愿容易在中间环节流失。
- 平台方需要人工处理大量低价值的转述工作。
- 联系发生在平台之外，平台无法沉淀需求、处理状态、成功率和后续服务价值。

本功能将平台角色从“人工传话者”变为“建联流程和线索管理者”：平台不公开联系方式，但保留申请、通知、处理、授权和成功建联记录。

## 3. 产品定位

### 3.1 一句话定位

围绕黑客松项目的双向授权建联工具。

### 3.2 核心价值

| 角色 | 价值 |
| --- | --- |
| 申请方 | 在项目详情页直接表达联系目的，减少等待和人工转述 |
| 项目方 | 在平台统一查看申请、筛选意向并决定是否交换联系方式 |
| 平台 | 掌握真实建联需求、项目方响应和有效连接数据，为后续推荐、撮合和商业化提供基础 |

### 3.3 产品原则

1. 联系申请必须围绕具体黑客松项目产生，不做无上下文的泛泛私信。
2. 项目方联系方式不公开，项目详情接口不得返回项目方私密联系方式。
3. 邮件只用于提醒和引导登录，不承担联系方式交换功能。
4. 联系方式采用双方授权后解锁，而不是平台单方面转交。
5. 项目方拥有接受、忽略和后续处理权，平台不替项目方自动同意。
6. 平台保留完整的申请和处理记录，但非连接双方不直接查看双方明文联系方式。
7. 当前黑客松专用模型与已有 Talent 建联模型分开，避免改变现有 Talent 连接的业务规则。

## 4. 目标与非目标

### 4.1 本期目标

- 登录用户可以从黑客松项目详情页发起建联申请。
- 申请方可以填写联系目的、给项目方的消息和自己的联系方式。
- 项目方收到一封不含申请方联系方式的邮件提醒。
- 项目方登录后可以在统一“连接记录”页面看到并处理黑客松建联申请。
- 项目方接受时填写并授权自己的联系方式。
- 申请接受后，双方只能在对应连接记录中查看彼此本次授权的联系方式。
- 申请方可以在“连接记录”查看进度和最终结果。
- 平台可以统计申请量、处理量、接受率、邮件投递结果和有效建联量。

### 4.2 明确不在本期

- 不提供实时聊天、群聊、站内私信或语音视频。
- 不在公开项目页展示手机号、邮箱、微信等联系方式。
- 不在通知邮件中展示申请方联系方式。
- 不发送接受/忽略结果通知邮件（P0）。
- 不支持项目方批量导出申请人联系方式。
- 不提供项目方自动接受申请。
- 不提供复杂的项目团队成员权限管理；首期使用一个项目接收主体。
- 不把黑客松项目写入现有平台 `projects` 表。
- 不把本功能强行复用为 Talent Plaza 的普通用户连接。
- 不承诺双方最终合作结果，也不对联系方式交换后的线下行为担保。

## 5. 用户与权限

### 5.1 申请方

任何已登录 User 都可以申请联系黑客松项目方，前提是：

- 账号未被平台禁止使用建联功能；
- 项目当前仍可公开访问；
- 当日申请量未超过限制；
- 没有对同一项目存在 Pending 申请；
- 申请内容通过字段校验和基础内容安全检查。

申请方不要求拥有 TalentProfile，也不要求是 Founder。

### 5.2 项目方

项目方是被平台配置为某个黑客松项目接收人的平台 User。一个项目在 P0 只有一个接收主体，接收主体可代表项目团队处理申请。

项目方可以：

- 查看发给自己所负责项目的 Pending 申请；
- 查看申请方公开身份、项目上下文、联系目的和申请消息；
- 接受申请并授权自己的联系方式；
- 忽略申请；
- 查看自己历史处理过的申请；
- 查看已接受连接中的双方授权联系方式。

项目方不能：

- 查看尚未接受连接的申请方联系方式；
- 查看其他项目方的申请；
- 通过公开项目接口读取申请或联系方式。

## 6. 核心用户流程

### 6.1 申请方发起申请

1. 用户访问 `/hackathon/projects/[id]`。
2. 页面显示 `联系项目方` 按钮。
3. 未登录用户点击后跳转登录页，登录成功后返回原黑客松项目详情页，并重新打开申请弹窗；不会自动提交。
4. 已登录用户打开申请弹窗。
5. 用户填写：
   - 联系目的；
   - 给项目方的消息；
   - 本次愿意授权的微信号和/或邮箱。
6. 页面明确提示：
   - 提交后，申请方联系方式不会出现在发给项目方的邮件中；
   - 只有项目方接受申请并授权自己的联系方式后，双方联系方式才会解锁；
   - 联系方式按本次申请单独授权，不会公开到项目页或个人公开资料。
7. 用户确认提交。
8. 服务端创建 Pending 建联申请，并异步触发项目方邮件通知。
9. 页面显示“申请已发送，等待项目方回应”，并提供“查看连接记录”。

### 6.2 项目方收到邮件

邮件发送给项目配置的通知邮箱。邮件内容包括：

- 有新的黑客松项目建联申请；
- 项目名称、项目详情链接；
- 申请方公开昵称或“平台用户”；
- 建联目的；
- 申请方填写的消息；
- 申请时间；
- “登录平台处理申请”按钮；
- 隐私说明：申请方联系方式不会在邮件中展示，需登录平台处理后按双方授权规则查看。

邮件明确不包含：

- 申请方微信号；
- 申请方邮箱；
- 申请方手机号；
- 联系方式密文；
- 可直接回复并绕过平台流程的联系方式。

邮件中的链接只进入平台连接记录或指定申请详情页，不包含可泄露敏感信息的 token。未登录时由平台登录流程处理，登录后只能看到该项目方有权限看到的申请。

### 6.3 项目方处理申请

1. 项目方登录平台。
2. 进入 `/connections`，默认显示“收到的申请”，Pending 申请优先。
3. 申请卡片显示：
   - 黑客松项目名称和链接；
   - 申请方公开身份；
   - 建联目的；
   - 申请消息；
   - 申请时间；
   - 不显示申请方联系方式。
4. 项目方点击“接受”。
5. 系统打开联系方式授权弹窗，项目方至少填写微信号或邮箱之一。
6. 项目方确认授权。
7. 服务端在事务中写入项目方联系方式、将状态改为 Accepted、记录接受时间。
8. 申请方和项目方均可在连接记录中查看双方本次授权的联系方式。

项目方也可以点击“忽略”：

- 状态变为 Ignored；
- 申请方看到“暂未建立连接”；
- 双方均不能查看联系方式；
- 忽略后申请方可在至少 7 天冷却期后重新申请（见 7.4）。

### 6.4 申请方查看结果

申请方在 `/connections` 看到：

- Pending：等待项目方回应；
- Accepted：已建立连接，可查看对方联系方式；
- Ignored：暂未建立连接，不显示对方联系方式；
- Cancelled：申请已结束，不显示联系方式。

申请方自己的联系方式不会在 Pending 或 Ignored 状态中被其他用户读取。Accepted 后，双方各自只能看到本连接中双方授权的联系方式。

## 7. 状态机与业务规则

### 7.1 状态

沿用现有 `ConnectionRequestStatus` 数值语义，黑客松建联单独使用：

| 状态 | 值 | 说明 |
| --- | ---: | --- |
| Pending | 0 | 等待项目方处理 |
| Accepted | 1 | 项目方已接受，双方联系方式可见 |
| Ignored | 2 | 项目方忽略，联系方式不可见 |
| Cancelled | 3 | 因项目隐藏或接收主体失效结束 |

### 7.2 合法转换

```text
Pending -> Accepted
Pending -> Ignored
Pending -> Cancelled
```

Accepted、Ignored、Cancelled 为终态。重复点击接受或忽略必须幂等：

- 已 Accepted 再次接受，返回当前 Accepted 记录，不要求重新填写联系方式；
- 已 Ignored 再次忽略，返回当前 Ignored 记录；
- 已处理状态不能再执行另一种处理动作。

### 7.3 创建规则

- 目标项目必须存在于黑客松活动数据源，且当前未被隐藏。
- 目标项目必须属于配置的黑客松活动，P0 为 event 4。
- 目标项目必须有有效接收主体。
- 申请方不能是该项目当前配置的接收主体。
- 同一申请方对同一项目最多一条 Pending 申请。
- 申请方对同一项目存在 Accepted 记录时，不得再次创建新申请；页面引导查看已有连接。
- 项目方接受人变更不改变既有连接；历史申请保留原始接收主体。
- 项目被隐藏后不得创建新申请；已有 Pending 申请转为 Cancelled，已有 Accepted 连接保留。
- 申请方每日最多创建 3 条黑客松项目 Pending 申请；P0 先使用固定值，后续可按账号信誉调整。
- 申请消息长度为 30 至 500 字，去除首尾空格，不允许控制字符。
- 目的从固定枚举中选择，建议首期使用：`试用产品`、`合作交流`、`加入项目`、`提供专业帮助`、`寻求反馈`、`其他`。
- 每次至少授权一种联系方法；支持微信号、邮箱。联系方式在服务端校验、规范化并加密。

### 7.4 重新申请策略

P0 允许 Ignored 申请重新发起，但必须满足：

- 距离上次 Ignored 至少 7 天；
- 仍受每日申请量限制。

这样既避免误操作导致永久阻断，也避免用户频繁骚扰项目方。

## 8. 页面与交互需求

### 8.1 黑客松项目详情页

现有页面：`/hackathon/projects/[id]`。

新增内容：

- 在项目详情页的侧栏或项目概要区域增加 `联系项目方` 主按钮；
- 已登录且存在 Pending/Accepted 记录时，显示当前状态而不是重复提交按钮；
- 项目方查看自己的项目时不显示联系自己的按钮；
- 项目隐藏或无有效接收主体时不显示可提交按钮，并显示“暂不可发起联系”；
- 未登录点击按钮后返回原页面；
- 申请弹窗支持移动端滚动和键盘操作；
- 发送中禁用按钮，防止重复提交。

申请弹窗字段：

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 联系目的 | 是 | 固定枚举单选 |
| 给项目方的消息 | 是 | 30-500 字 |
| 微信号 | 条件必填 | 1-64 字符，无控制字符 |
| 邮箱 | 条件必填 | 合法邮箱，最长 254 字符 |
| 隐私确认 | 是 | 明确确认双方接受后交换联系方式 |

不支持用户在表单中填写项目方联系方式，也不展示项目后台已有的团队联系人字段。

### 8.2 连接记录页

复用现有 `/connections` 页面和入口，但增加来源类型和黑客松项目展示。

页面分区：

- `收到的申请`：当前用户作为黑客松项目方接收人的申请；
- `我发起的`：当前用户发出的黑客松申请；
- `已建立连接`：Accepted 记录；
- `已结束`：Ignored / Cancelled 记录。

黑客松连接卡片显示：

- 来源标签：`黑客松项目`；
- 项目名称、项目封面缩略图或项目 ID；
- 对方昵称和头像；
- 对方是否有公开 TalentProfile；
- 联系目的；
- 消息；
- 申请时间和处理时间；
- 状态；
- 接受后显示双方联系方式，并提供复制按钮。

隐私要求：

- Pending 卡片永远不返回对方联系方式；
- Ignored / Cancelled 卡片永远不返回联系方式；
- Accepted 只返回当前连接双方的 `mine` 和 `other` 联系方式；
- 列表接口不得返回联系方式密文；
- 前端不将联系方式写入 URL、localStorage、埋点参数或错误提示。

### 8.3 邮件失败提示

创建申请不应因为邮件服务暂时失败而回滚。申请仍然创建成功，项目方可以在平台连接记录中看到申请。

申请方看到：

> 申请已发送。平台正在通知项目方，你也可以在连接记录中查看处理进度。

如果邮件最终投递失败：

- 系统记录失败原因和重试次数；
- 自动重试有限次数；
- 页面不把项目方邮箱或底层错误暴露给申请方；
- 系统按重试策略自动重试；失败时不影响申请记录和连接记录中的状态。

## 9. 邮件通知需求

### 9.1 发送时机

申请事务提交成功后，异步发送“新的黑客松项目建联申请”邮件。

不在数据库事务内直接调用外部邮件服务，避免外部请求阻塞事务或导致事务不一致。

### 9.2 收件人解析

黑客松项目来自外部活动数据库，现有数据只有项目展示字段，未提供平台 User 与项目负责人的可靠关联。因此必须新增“项目接收主体配置”能力。

P0 推荐建立平台侧映射：

- `event_id + hackathon_project_id` 映射到一个 `receiver_user_id`；
- 保存一个用于通知的 `notification_email`；
- 可选保存项目方展示名称；
- 接收主体映射以预置数据方式维护，本期不提供后台配置界面。

`receiver_user_id` 是登录平台后查看申请和处理申请的权限依据；`notification_email` 只负责投递提醒，不能单独授予查看权限。

如果后续外部活动系统能够提供项目负责人 user ID 和邮箱，可增加同步任务替代人工配置，但仍应把最终权限映射落在平台侧。

### 9.3 邮件内容

邮件主题：

```text
[Shenicest] 你的黑客松项目收到一条新的建联申请
```

邮件正文包含：

- 项目名称和项目页链接；
- 申请方昵称；
- 联系目的；
- 申请消息；
- 申请时间；
- 处理申请按钮；
- 隐私和安全说明。

邮件正文不得包含：

- 微信、邮箱、手机号；
- `senderContact` 字段的任何序列化结果；
- 数据库 ID 以外的敏感内部字段；
- 可绕过鉴权打开申请的长效 token。

### 9.4 邮件幂等与重试

以 `connection_request_id + notification_type` 作为幂等键。

建议邮件投递记录状态：

| 状态 | 说明 |
| --- | --- |
| Pending | 待发送 |
| Sending | 发送中 |
| Sent | 邮件服务接受 |
| Failed | 最终失败 |

重试建议：首次失败后按 1 分钟、5 分钟、30 分钟退避，最多 3 次。重复消费不能发送重复邮件。

### 9.5 邮件服务

邮件发送走腾讯云 SES 的 **SMTP 通道**。腾讯云 SES 的 `SendEmail` API 默认仅支持模板发送（`Simple` 自定义内容参数已废弃，仅历史申请过特殊配置的账号可用），而 SMTP 直接携带原始 HTML / 纯文本正文，无需控制台模板。平台新增一个薄适配层隔离供应商细节，接口至少包含：

```ts
interface Mailer {
  send(input: {
    to: string
    subject: string
    html: string
    text: string
    idempotencyKey: string
  }): Promise<{ providerMessageId?: string }>
}
```

实现要求：

- 使用 SMTP（`nodemailer`）发送 HTML 与纯文本正文，复用已验证的发信域名/发信地址（腾讯云 SES 控制台为发信地址生成 SMTP 专用密码）；
- 发件人显示名为 `SheNicest`（`SMTP_FROM_NAME`，可选覆盖），收件端不展示裸邮箱本地部分（如 `notification@...`）；
- SMTP 凭据（host / port / user / pass）通过环境变量注入，禁止写入代码、仓库或日志；
- 需要配置 SMTP 服务地址（如 `smtp.qcloudmail.com` 香港区 / `gz-smtp.qcloudmail.com` 广州区）、端口（465，隐式 TLS）、发件人地址和回复地址；
- 发送成功后记录 SMTP 返回的 `MessageId`，写入投递记录的 `provider_message_id`；
- 适配层负责凭据读取、供应商错误归一化和投递状态记录；测试环境用内存实现替换 Mailer，不真实发信。

## 10. 技术方案概览

### 10.1 领域建模决策

本期新增 `HackathonConnectionRequest`，不直接复用现有 `connection_requests` 表。

原因：

- 现有 `ConnectionRequest` 的接收方前提是拥有 Published TalentProfile；黑客松项目方不应被强制要求创建 TalentProfile。
- 现有 `projectId` 语义是“发送方关联的自己的 Project”；黑客松建联的项目是申请方想联系的目标项目，语义相反。
- 黑客松项目来自外部活动数据库，不是本地 `projects` 表。
- 直接扩大现有表会引入 nullable 多态字段、混淆项目所有权和复杂的兼容分支。
- 独立表可以保持已有 Talent 建联稳定，同时复用加密联系方式、状态枚举、连接记录 UI 和通用服务能力。

未来如果平台项目也需要建联，再评估将两者抽象为统一的 `ConnectionTarget` / `ConnectionRequest` 模型；不要在本期提前引入过度泛化的多态表。

### 10.2 新增数据表：hackathon_project_contacts

用途：配置黑客松项目的接收主体和通知地址。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | int | 主键 |
| `event_id` | int | 外部活动 ID，P0 为 4 |
| `hackathon_project_id` | int | 外部黑客松项目 ID |
| `receiver_user_id` | varchar(255) | 平台登录用户 ID |
| `notification_email` | varchar(254) | 项目方邮件提醒地址 |
| `display_name` | varchar(255) nullable | 项目方展示名称 |
| `created_at` | timestamp | 创建时间 |
| `updated_at` | timestamp | 更新时间 |

约束和索引：

- 唯一约束：`(event_id, hackathon_project_id)`；
- `receiver_user_id` 索引；
- `notification_email` 不作为鉴权依据；
- 允许未来扩展为一个项目多个接收人，但 P0 API 只允许一个有效接收主体。

### 10.3 新增数据表：hackathon_connection_requests

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | int | 主键 |

| `hackathon_project_id` | int | 目标黑客松项目 ID |
| `receiver_user_id` | varchar(255) | 创建时锁定的项目方平台 User ID |
| `sender_user_id` | varchar(255) | 申请方平台 User ID |
| `purpose` | varchar(64) | 固定建联目的 |
| `message` | text | 申请方消息 |
| `sender_contact` | text | 加密后的申请方联系方式 |
| `receiver_contact` | text nullable | 加密后的项目方联系方式 |
| `status` | tinyint | Pending / Accepted / Ignored / Cancelled |
| `pair_key` | varchar(511) nullable | 可选，用于限制同一用户与同一目标重复申请 |

- `(receiver_user_id, status, created_at)`：查询项目方待处理申请；
- `(event_id, hackathon_project_id, status)`：查询项目申请；
- `(sender_user_id, hackathon_project_id, status)`：重复申请检查；
- 对 Pending 申请实现唯一约束。若 MySQL 不支持条件唯一索引，应通过 `pair_key`：Pending 时写入，转为终态时置空，并结合事务锁处理并发。

### 11.1 申请方接口

#### `POST /hackathon/projects/:id/connections`

创建黑客松项目建联申请。

请求：

```json
{
  "purpose": "合作交流",
  "message": "我们正在做相近方向的产品，希望和你们交流产品设计与用户验证经验。",
  "wechat": "example_wechat",
  "email": "user@example.com"
}
```

规则：

- `auth: true`；
- 服务端调用黑客松项目查询逻辑确认项目存在且未隐藏；
- 查询有效项目接收主体；
- 校验状态、重复申请、每日限额和联系方式；
- 加密申请方联系方式；
- 事务内创建申请和邮件投递任务；
- 响应不得包含联系方式明文或密文。

响应建议：

```json
{
  "id": 123,
  "eventId": 4,
  "hackathonProjectId": 456,
  "status": 0,
  "createdAt": "2026-09-07T10:00:00.000Z"
}
```

错误：

| HTTP | code | 场景 |
| ---: | --- | --- |
| 401 | `UNAUTHORIZED` | 未登录 |
| 404 | `PROJECT_NOT_FOUND` | 项目不存在或已隐藏 |
| 409 | `NO_RECEIVER_CONFIGURED` | 项目没有配置项目方 |
| 409 | `PENDING_EXISTS` | 已有 Pending 申请 |
| 409 | `ALREADY_CONNECTED` | 已经 Accepted |
| 409 | `RATE_LIMITED` | 超过每日限制 |
| 422 | `INVALID_CONTACT` / `INVALID_MESSAGE` | 参数不合法 |

#### `GET /hackathon/projects/:id/connections/me`

返回当前用户针对该项目的可见状态摘要，不返回联系方式，供详情页决定按钮状态。

响应：

```json
{
  "data": {
    "id": 123,
    "status": 0,
    "createdAt": "2026-09-07T10:00:00.000Z"
  }
}
```

无记录时返回 `{ "data": null }`。

### 11.2 连接记录接口

#### `GET /connections`

扩展现有连接记录聚合接口，返回 Talent 和 Hackathon 两种来源的统一展示 DTO。

建议查询参数：

- `source=all|talent|hackathon`；
- `direction=all|sent|received`；
- `status=pending|accepted|ignored|cancelled`；
- `offset`、`limit`。

统一 DTO 增加：

```ts
{
  source: 'talent' | 'hackathon'
  target: {
    type: 'talent_user' | 'hackathon_project'
    projectId?: number
    eventId?: number
    name?: string
    url?: string
  }
}
```

联系方式只在 `Accepted` 且当前用户属于申请双方时通过 DTO 的 `contacts` 字段返回。推荐继续采用 `mine` / `other` 结构，避免前端根据方向误判。

#### `POST /connections/hackathon/:id/accept`

项目方接受申请并授权联系方式。

请求：

```json
{
  "wechat": "founder_wechat",
  "email": "founder@example.com"
}
```

规则：

- 当前用户必须是申请创建时锁定的 `receiver_user_id`；
- 申请必须为 Pending；
- 目标项目仍可读取时接受；若项目已经隐藏，返回冲突并转为 Cancelled 的策略需明确，推荐先由状态检查拒绝并由后台任务取消；
- 至少一个联系方式；
- 事务内加行锁，写入加密后的 `receiver_contact`，并更新状态；
- 重复接受幂等，不能覆盖原授权联系方式。

#### `POST /connections/hackathon/:id/ignore`

仅锁定的项目方接收人可调用。Pending 转 Ignored，重复调用幂等。

#### `GET /connections/hackathon/:id/contacts`

仅 Accepted 申请的 sender 或 receiver 可调用。返回：

```json
{
  "mine": { "wechat": "...", "email": null },
  "other": { "wechat": null, "email": "..." }
}
```

读取前必须同时校验：

- 记录存在；
- 状态为 Accepted；
- 当前用户是 sender 或 receiver。

### 11.3 黑客松服务接口改动

现有 `HackathonService` 已能从外部活动数据库读取项目详情。建议新增：

## 13. 安全与隐私

### 13.1 联系方式

- 继续复用 `apps/api/src/lib/contact-encryption.ts` 的服务端 AES-GCM 加密能力；
- 申请方和项目方联系方式都按每条连接单独加密；
- 密钥必须由 `SHENICEST_CONTACT_ENCRYPTION_KEY` 提供，生产环境独立管理；
- 明文不能写入日志、异常、邮件、审计、埋点、缓存或数据库；
- API 响应中不能返回密文；
- 联系方式读取必须做资源级鉴权；
- 前端只在 Accepted 状态下请求或渲染联系方式。

### 13.2 邮件

- 邮件模板使用转义后的用户输入，防止 HTML 注入；
- 纯文本版本和 HTML 版本都必须提供；
- 申请消息不能未经处理直接作为 HTML 插入；
- 邮件中不放联系方式；
- 邮件链接不携带可直接授权的 token；
- 邮件投递地址属于受限数据，不进入普通连接响应。

### 13.3 内容滥用

- 每日发起数量限制；
- 同项目 Pending 唯一限制；
- Ignored 重试冷却；
- 控制字符和超长内容拒绝；
- 预留敏感词/垃圾消息检测接口；
- 预留举报和平台禁用发送权限；
- 后续增加用户级 block 时，不改变已 Accepted 连接的历史可见性规则，具体策略另行定义。

## 14. 通知与一致性设计

申请创建的关键一致性要求是：申请记录不能因为邮件服务失败而丢失，邮件不能因为重复请求而重复发送。

推荐流程：

1. HTTP 请求校验用户、项目和接收主体。
2. 开启数据库事务。
3. 锁定同项目已有 Pending 记录和申请限额记录。
4. 写入黑客松连接申请。
5. 写入邮件投递任务，使用唯一幂等键。
6. 提交事务。
7. 独立 worker 读取待发送任务并调用 Mailer。
8. 更新发送状态和重试信息。

如果 worker 不可用，连接记录仍可由项目方在平台中查看；邮件服务恢复后由 worker 按投递任务继续发送。

接受流程必须在一个事务内完成：

1. 锁定连接申请。
2. 校验当前用户为 receiver 且状态为 Pending。
3. 校验并规范化联系方式。
4. 加密 receiver contact。
5. 更新状态为 Accepted、写入 acceptedAt 和 handledAt。
6. 提交事务。

## 19. 后续扩展到平台 Project

本期代码和数据设计需要保留以下扩展边界：

- `sender_contact` / `receiver_contact` 加密逻辑抽为共享服务；
- 邮件投递记录不绑定黑客松业务名称，使用通用 notification type；
- 连接记录 DTO 使用 `source` 和 `target`，不要把页面写死为 Talent；
- 黑客松项目接收主体配置未来可抽象为 `ConnectionTargetOwner`；
- API 未来可以提供统一的“向目标发起连接”能力，但本期保持黑客松和 Talent 的数据表独立；
- 平台 `Project` 接入时，目标项目可以直接引用本地 `projects.id`，并增加项目方联系方式接收配置；
- 未来可以增加站内消息、邮件回复代理、项目方需求标签和平台撮合服务，但不应破坏双方授权规则。

## 20. 验收标准

功能可验收的最小闭环如下：

1. 平台以预置数据为一个黑客松项目配置接收人和通知邮箱。
2. 普通登录用户在该项目详情页点击 `联系项目方`。
3. 用户填写目的、消息和自己的联系方式并提交。
4. 数据库生成一条 Pending 黑客松连接记录，联系方式为密文。
5. 项目方收到邮件，邮件包含项目、消息和处理入口，但不包含申请方联系方式。
6. 项目方登录后在 `/connections` 看到该申请，非项目方看不到。
7. 项目方接受并填写自己的联系方式。
8. 记录变为 Accepted，双方均可以在平台连接记录查看对方本次授权的联系方式。
9. 未接受时，任何一方都不能查看对方联系方式。
10. 重复提交、重复接受、重复忽略不会创建重复记录或覆盖联系方式。
11. 项目隐藏、接收主体失效、邮件失败等异常场景有明确状态和后台可追踪记录。

## 21. 已确认的产品决策

以下问题已在产品评审中确认：

1. 一个黑客松项目对应一个项目方账号，即一个接收主体。
2. 项目方接收邮箱（`notification_email`）不强制与 `receiver_user_id` 的登录邮箱一致，但归属由平台确认。
3. 申请方必须至少授权一种联系方式（微信号或邮箱），不允许只写消息。
4. 项目方忽略后，申请方允许重新申请；沿用 7.4 的规则：距上次 Ignored 至少 7 天。
5. 项目隐藏后，已有 Pending 申请自动转为 Cancelled，历史记录保留。
6. 申请方通过连接记录查看状态（P0 忽略不发结果邮件；产品后续决策：项目方**接受**时向发送方平台账号邮箱发送结果通知邮件，即该邮件从 P1 提前实现，复用现有投递 worker，收不到账号邮箱时静默跳过）。
7. P0 不提供“暂时关闭新申请”开关；`hackathon_project_contacts` 不含 `is_active` 字段，P1 引入时再加列。
8. 腾讯云 SES 的发信域名和发信地址沿用现有配置，SMTP 专用密码由控制台生成，无需新建。
