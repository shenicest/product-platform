# 0016. 赛季发布就绪使用真实的最小依赖，不用假数据

## Status

Accepted

## Context

BoomLand 的九项发布门槛包含命题、预算、积分池、评委分配、核验员等配置。本批范围只做“开赛前赛季 + 用户报名”，评分、结算、作品、里程碑都不做。

有两种做法：

- **A. 只做赛季和报名，把其余门槛做成占位/假数据**，让赛季能快速批准。
- **B. 九项门槛全部硬校验，并为预算、积分池、评委分配、核验员建最小真实表与配置接口/UI**。

A 的问题：赛季可以在没有任何命题、预算、积分池的情况下公开并接受报名，报名者看到的是一个无法开赛的空壳；同时无法端到端验证“配置 → 提交 → 批准 → 开赛 → 报名”的真实流程。占位数据还会在后续模块落地时造成迁移和语义债务。

## Decision

1. **九项发布就绪全部硬校验**，主办方提交与管理员批准都必须 `ready=true`。
2. **命题做完整五件套**（创建、编辑、发布、关闭、归档、版本计数）。
3. **其余四项做最小真实依赖**：
   - 预算：版本化、active 版本、金额 > 0、追加原因；
   - 积分池：总分、已分配、已使用、总量 > 0；
   - 评委分配：按评委分配额度，受限积分池总量；
   - 核验员授权：active/revoked，发布要求至少一条 active。
   只实现让门槛成立所需的字段与接口/UI，不实现评分、结算、回收后的复杂流程。
4. **不伪造门槛数据**：任何一项未配置，赛季不能提交/批准。
5. **表结构可被后续完整模块扩展**，但本批不预埋未使用的评分/结算字段。

## Consequences

- 本批需要新增 5 张最小依赖表（`season_budgets`、`season_point_pools`、`point_allocations`、`season_verifier_grants`）以及命题表。
- 后续做评分/结算时，需要在不破坏现有数据的前提下扩展这些表。
- 可以端到端跑通“配置 → 就绪 → 待批 → 批准 → 开赛 → 报名 → 接受报名 → 微信群状态”的完整闭环，测试价值高。
- 主办方配置成本上升；通过复制上季配置与合理默认值缓解。
