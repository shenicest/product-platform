# 【PRD】人才广场 Standalone

> 文档状态：Draft
> 版本：v1.0
> 更新日期：2026-08-17
> 相关资料：[Standalone 交互示意](./talent-plaza-standalone.html)

## 1. 文档目的

本文定义“人才广场 Standalone”的产品目标、版本范围、核心流程、页面规则、匹配逻辑与验收标准，作为产品评审、设计、技术方案和研发拆分的共同依据。

“Standalone”表示本功能在产品展示平台中拥有独立入口、独立页面和独立业务闭环。本功能确定作为现有站点内的独立模块建设，复用平台登录身份、同源 Cookie、导航和已上线项目信息，不使用独立域名或独立登录；它不依赖用户先成为 Founder，也不改变现有 Project、Founder、Like、Follow 等领域规则。

## 2. 背景与问题

当前平台以“发现项目”为核心，用户可以查看项目和 Founder，但缺少从“找合作者”出发的人才发现路径：

- 项目发起人无法按技能、角色和合作偏好主动找人。
- 有能力参与项目的用户缺少结构化展示自身能力和合作意愿的入口。
- 用户需要逐个查看项目才能推断某个人是否适合合作，发现效率低。
- 用户即使找到潜在合作者，也没有带目的、带项目上下文的连接请求闭环。

人才广场通过公开人才档案、结构化筛选、可解释匹配和连接请求，降低找到潜在合作者并建立第一次联系的成本。

## 3. 产品定位

### 3.1 一句话定位

面向早期产品社区的公开人才发现与合作连接平台。

### 3.2 核心价值

- 对找人的用户：快速找到能力互补、合作方向合适的人。
- 对展示自己的用户：用技能、已上线项目和合作偏好表达“我能做什么、我想参与什么”。
- 对平台：把项目浏览关系延伸为真实协作关系，提高用户和项目的长期活跃度。

### 3.3 非目标

- 不做职位发布、简历投递、Offer 和入职管理等招聘系统能力。
- 不做薪酬结算、合同签署、工时管理或劳动关系担保。
- 不承诺匹配分代表合作成功概率。
- 不在首版提供实时聊天、群聊或音视频沟通。
- 不公开手机号、邮箱、微信等私人联系方式。

## 4. 目标与指标

### 4.1 产品目标

1. 让登录用户在 5 分钟内完成可公开的人才档案。
2. 让浏览者通过搜索和筛选，在 3 次操作内缩小到有价值的候选人集合。
3. 让匹配结果具备可解释性，用户可以理解“为什么推荐这个人”。
4. 打通“发现人才 → 查看档案 → 发起连接 → 对方处理”的最小闭环。

### 4.2 核心指标

| 指标       | 定义                                | 首版建议观察目标 |
| -------- | --------------------------------- | -------- |
| 人才档案完成率  | 已开始编辑且达到可发布条件的用户数 / 已开始编辑用户数      | ≥ 60%    |
| 广场到档案点击率 | 人才详情访问次数 / 人才卡片曝光次数               | ≥ 15%    |
| 档案到连接转化率 | 成功发送连接请求人数 / 人才详情独立访问人数           | ≥ 5%     |
| 连接接受率    | 已接受请求数 / 已处理请求数                   | ≥ 25%    |
| 有效候选覆盖率  | 至少出现 1 位匹配候选人的已发布档案用户数 / 已发布档案用户数 | ≥ 80%    |

首版以建立基线为主，目标值用于上线后判断漏斗是否健康，不作为阻断上线的硬门槛。

## 5. 用户与场景

### 5.1 用户角色

| 用户       | 说明                    | 核心诉求                  |
| -------- | --------------------- | --------------------- |
| 游客       | 未登录访问者                | 浏览人才和公开档案，判断社区质量      |
| 普通用户     | 已登录，但不要求拥有 Founder 身份 | 创建人才档案、找项目或找合作伙伴      |
| Founder  | 持有 `Role.Founder` 的 User | 为自己的项目寻找设计、研发、运营或增长伙伴 |
| Operator | 平台运营人员                | 处理违规档案和连接滥用，不参与普通连接流程 |

### 5.2 核心场景

1. Founder 为一个已上线项目寻找全栈开发者，筛选“开发、全栈开发”，查看候选人的项目经历后发起连接。
2. 设计师发布人才档案，声明希望参与女性健康产品，并接收带项目上下文的连接请求。
3. 独立开发者浏览互补人才，通过匹配原因发现擅长用户研究和增长的潜在伙伴。
4. 游客浏览人才广场；尝试连接时登录，登录后返回原人才档案继续操作。

## 6. 版本范围

### 6.1 P0：MVP 必须实现

- 独立人才广场入口和列表页。
- 人才档案创建、编辑、发布、暂停公开。
- 公开人才详情页。
- 关键词、角色、技能和合作周期筛选。
- 按最近活跃、最新加入排序；P0 不按匹配度排序。
- 人才详情页面向访问者和已发布档案候选人提供可解释匹配分和匹配原因；匹配分不用于列表排序。
- 游客或没有人才档案的用户看到不带个性化分数的列表。
- 连接请求的发送、接收、接受和忽略。
- 请求双方查看连接状态。
- 双方确认连接后交换各自授权的联系方式。
- “我的连接”提供未处理连接数量提醒；接收方可从顶部导航或用户菜单进入待处理请求。P0 不提供站内通知、邮件通知、轮询或实时推送，数量仅在页面加载、路由进入或手动刷新时更新。
- 隐私控制、联系运营入口和 Operator 下架能力。
- 核心行为埋点和基础漏斗指标。

### 6.2 P1：后续增强

- 收藏或关注人才。
- “为某个 Project 找人”的项目缺口模板和项目级匹配。
- 站内通知和邮件通知。
- 接受连接后开放站内私信。
- 项目贡献确认和他人背书。
- 基于查看、连接、接受和忽略行为优化推荐排序。
- 团队批量邀请和多人协作空间。

### 6.3 明确不在本期

- 实时聊天、语音和视频。
- 招聘职位、简历投递、面试和 Offer 流程。
- 付费置顶、会员或商业撮合收费。
- AI 自动生成档案或黑盒推荐模型。
- 对公开互联网进行人才资料抓取。
- 原生移动端 App。

## 7. 核心概念

以下是本功能拟新增的产品概念。进入技术设计前，需同步补充 `CONTEXT.md` 并按需要创建 ADR。

### 7.1 TalentProfile（人才档案）

User 在人才广场中的结构化公开档案。一个 User 最多有一个 TalentProfile。人才档案与 Founder 身份独立，未提交 Project 的 User 也可以创建。

状态：

- `Published`：已发布，可在广场和公开详情中展示。
- `Paused`：用户主动暂停公开，不出现在广场，旧公开链接显示“档案暂不可见”。不能接收新请求；暂停前已有的 `Pending` 请求仍可处理，已有 `Accepted` 连接及联系方式继续可见。用户仍可作为发送方发起新请求。
- `Suspended`：Operator 因违规下架，不公开展示。该状态为终态，用户不能自行恢复或重新发布；如需修改或申诉，页面提示联系运营。用户不能发送或处理连接请求，涉及该用户的 `Pending` 请求不计入双方未处理数量；已有 `Accepted` 连接及联系方式继续对双方可见。

### 7.2 Skill（技能）

平台维护的标准技能词条，用于档案、筛选和匹配。用户只能从标准技能库选择，首版不允许自由创建新技能；可通过反馈入口申请补充。

首批技能词库：

| 角色分类 | 技能 |
| --- | --- |
| 产品 | 产品策略、需求分析、用户研究、产品设计、原型设计、项目管理 |
| 设计 | UI 设计、UX 设计、交互设计、视觉设计、品牌设计、动效设计 |
| 开发 | 前端开发、后端开发、全栈开发、移动端开发、AI 开发、数据开发、DevOps、硬件开发 |
| 增长/内容 | 增长策略、内容策划、内容创作、社交媒体、SEO、品牌传播 |
| 运营 | 用户运营、社区运营、活动运营、商业运营、客户成功 |
| 数据 | 数据分析、数据可视化、实验设计、商业分析 |
| 其他 | 商业策略、融资、法务、财务、行业研究 |

P0 使用固定技能词库。不提供 Operator 启用、停用、新增技能，也不允许用户自由创建技能。

### 7.3 CollaborationPreference（合作偏好）

TalentProfile 中用于表达期望角色、偏好项目领域和合作周期的结构化信息。

### 7.4 ConnectionRequest（连接请求）

一个 User 向另一个已发布人才档案的 User 发出的合作意向。请求可以关联一个自己拥有的 Project，也可以不关联项目。

状态：

- `Pending`：等待接收方处理。
- `Accepted`：接收方接受。
- `Ignored`：接收方忽略。
- `Cancelled`：请求因关联用户的档案被 `Suspended` 等系统原因结束，双方不能继续处理。

### 7.5 与现有领域的关系

- TalentProfile 始终属于 User，不等同于 UserIdentity，也不自动授予 Founder 角色。
- 人才档案自动展示 User 作为 Founder 的 Live Project，不要求用户手动选择或填写证明；Draft、Pending Review、Rejected 和 Delisted 状态的 Project 不公开展示。
- 现有 Follow 只能关注持有 Founder 角色的 User。P0 不复用 Follow 表达“关注人才”，避免改变 Follow 的既有语义。
- ConnectionRequest 是合作意向，不是 Follow、Comment 或 ProjectEditProposal。

## 9. 核心流程

### 9.1 创建并发布人才档案

1. 登录用户进入“编辑我的档案”。
2. 系统读取外部 User 的昵称和头像，只允许用户在外部认证系统允许的范围内修改；本功能不直接写共享 User 表。
3. 用户填写定位、简介、技能、期望角色和合作偏好；未发布前的数据仅保留在当前页面，不创建 TalentProfile，也不支持保存草稿。为避免刷新或离开页面导致内容丢失，前端使用浏览器本地临时保存；本地临时数据不得上传服务端或参与匹配。
4. 用户点击“发布档案”，系统校验全部发布必填项。
5. 人才档案采用先发后审：发布成功后创建 TalentProfile，状态立即为 `Published` 并进入人才广场，无需等待 Operator 首次审核。P0 不提供自动内容审核，发布后由 Operator 通过联系运营和日常巡检处理违规档案。
6. 用户可随时编辑已发布档案；保存成功后立即更新，不走 Project 审核流程。
7. 用户可暂停公开；暂停后不再被搜索和匹配。

### 9.2 浏览与筛选人才

1. 用户进入人才广场，默认看到已发布且未被屏蔽的人才档案。
2. 游客或没有人才档案的用户默认按最新加入排序，不展示个性化匹配分。
3. 所有访问者默认按最新加入排序；P0 不按匹配度排序。人才匹配分和原因仅在人才详情页、且访问者和候选人均有 Published TalentProfile 时展示。
4. 用户通过关键词和筛选条件缩小结果。
5. 筛选条件写入 URL，支持刷新、返回和分享筛选结果。
6. 点击人才卡片进入公开档案。

### 9.3 发起连接

1. 用户在人才卡片或详情页点击“发起连接”。
2. 游客先登录，成功后回到原页面并重新打开连接表单，不自动发送。
3. 发送方必须已登录，不要求拥有 TalentProfile。若发送方拥有 TalentProfile，则其状态不能为 `Suspended`；`Published` 和 `Paused` 状态均可发起请求。发送方没有 TalentProfile 时，不参与匹配计算。
4. 用户选择是否关联一个自己拥有的 Live Project。
5. 用户选择合作目的并填写个性化说明。
6. 系统展示请求预览，用户确认后发送。
7. 发送成功后按钮显示“等待回应”，并可在“我的连接”查看状态。

### 9.4 处理连接请求

1. 接收方从顶部导航或用户菜单看到“我的连接”未处理数量，点击后进入收到的请求列表。
2. 接收方可查看发送方公开档案、关联 Project 和合作说明。
3. 接收方选择“接受”或“忽略”。
4. 接收方点击“接受”后，必须填写并确认自己愿意分享的联系方式；联系方式校验成功后，请求才可变为 `Accepted`。
5. 连接状态变为 `Accepted` 后，双方才能看到对方在本次连接中授权分享的联系方式，并可复制微信号或通过邮箱联系。
6. 联系方式只对该连接双方可见，不进入公开人才档案；任意一方未确认前，平台不向对方展示其联系方式。
7. 忽略后，发送方只看到“暂未建立连接”，不展示“对方忽略了你”等具有压迫感的文案。因系统原因取消时，发送方看到“连接请求已结束”。

#### 档案状态对连接的影响

| 档案状态 | 发送新请求 | 接收新请求 | 处理已有 Pending | Pending 是否计入提醒 | 查看已有 Accepted 联系方式 |
| --- | --- | --- | --- | --- | --- |
| `Published` | 是 | 是 | 是 | 是 | 是 |
| `Paused` | 是 | 否 | 是 | 是 | 是 |
| `Suspended` | 否 | 否 | 否 | 否 | 是 |

接收新请求以请求创建时接收方的档案状态为准；接收方必须拥有 `Published` TalentProfile。发送方只需已登录；若发送方拥有 TalentProfile，则其状态不能为 `Suspended`，`Published` 和 `Paused` 均可发起请求。用户从 `Paused` 恢复为 `Published` 后，可以重新接收新请求。`Suspended` 为终态，不能恢复。任一方的档案被置为 `Suspended` 时，与其相关的 `Pending` 请求自动转为 `Cancelled`，不计入未处理数量且不能继续处理。

## 10. 页面需求

### 10.1 人才广场

#### 页面目标

帮助用户快速理解人才广场价值，并找到值得进一步了解的潜在合作者。

#### 页面结构

1. 顶部导航。
2. Hero：标题、价值说明和“完善我的档案”入口。
3. 个人匹配摘要：仅已登录且已发布档案用户展示。
4. 搜索、筛选与排序区域。
5. 人才结果列表。
6. 分页和空状态。

#### 筛选项

| 筛选项             | 规则                              |
| --------------- | ------------------------------- |
| 关键词 `q`         | 匹配昵称、个人定位、简介、技能名称和公开 Project 名称 |
| 角色 `role`       | 单选；产品、设计、开发、增长/内容、运营、数据、其他      |
| 技能 `skills`     | 多选；同一组内默认满足任一技能                 |
| 合作周期 `duration` | 多选；一次咨询、短期项目、长期合作               |

不同筛选项之间为 AND；同一多选筛选项内部为 OR。修改筛选后回到第一页。

#### 排序

- `active`：最近活跃时间从近到远；最近活跃时间取 TalentProfile 最近更新时间，不使用登录时间或其他隐私行为。
- `new`：TalentProfile 首次发布时间从近到远。

默认 `new`。相同排序值依次按档案完整度、最近更新时间和 userId 稳定排序。

#### 人才卡片字段

- 头像、昵称。
- 个人定位和期望角色。
- 不超过 80 字的简介摘要。
- 最多 5 个核心技能。
- 用户拥有的 Live Project；卡片最多展示 1 个，优先展示最近上线的项目。
- 合作周期。
- 列表不展示匹配分；匹配分与原因仅在人才详情页、且双方均有 Published TalentProfile 时展示。
- “查看档案”和“发起连接”按钮。

#### 分页

- 每页 20 条。
- URL 保存 `page` 和筛选参数。
- 首版使用传统分页，不使用无限滚动。

#### 页面状态

| 场景       | 标题        | 说明                 | CTA    |
| -------- | --------- | ------------------ | ------ |
| 平台尚无人才档案 | 还没有公开人才档案 | 成为第一批展示能力的社区成员     | 完善我的档案 |
| 筛选无结果    | 没有符合条件的人才 | 调整技能或合作周期后再试       | 清空筛选   |
| 用户没有人才档案  | 建立你的技能画像  | 发布档案后可查看个性化匹配；登录后也可以直接发起连接 | 完善我的档案 |
| 数据加载失败   | 暂时无法加载人才  | 请稍后重试              | 重新加载   |

### 10.2 人才公开档案

#### 展示内容

- 头像、昵称、个人定位、所在城市（可选）。
- 个人简介。
- 核心技能，不展示熟练度或能力排名。
- 用户拥有的 Live Project，按最近上线时间排序，点击进入项目详情。
- 用户没有 Live Project 时，对本人展示“还没有可展示的项目，上传项目让更多人了解你的实践经历”，并提供“上传项目”入口；对其他访问者不展示空项目区。
- 期望角色和感兴趣的项目品类。
- 合作周期。
- 最近更新日期，不展示精确在线时间。
- 与当前用户的匹配分和原因。
- 发起连接、“联系运营”入口。“联系运营”通过邮箱反馈虚假资料、骚扰、广告、侵权或其他问题，不在站内提交举报表单。邮件入口使用部署配置的运营邮箱，并预填相关档案 URL。

#### 访问规则

- `Published` 档案公开访问。
- `Paused` 对本人显示恢复入口，对其他用户显示“档案暂不可见”。
- `Suspended` 对本人显示下架原因和“如需修改，请联系运营”，对其他用户显示“档案暂不可见”。
- 页面不得暴露手机号、邮箱、微信、精确住址和登录时间。

### 10.3 编辑我的档案

#### 字段规则

| 区域   | 字段      | 必填 | 规则                          |
| ---- | ------- | -- | --------------------------- |
| 基础信息 | 头像、昵称   | 是  | 来源于共享 User；本功能只读展示或跳转统一账号设置 |
| 基础信息 | 个人定位    | 是  | 2-30 字，例如“全栈开发者 / 独立开发者”    |
| 基础信息 | 个人简介    | 是  | 30-500 字                    |
| 基础信息 | 所在城市    | 否  | 用户自由填写城市名称，不使用指定城市列表；不收集详细地址 |
| 能力   | 核心技能    | 是  | 3-10 个标准技能                  |
| 合作偏好 | 期望角色    | 是  | 最多 3 个                      |
| 合作偏好 | 感兴趣的品类  | 是  | 最多 3 个，复用 `CATEGORIES`      |
| 合作偏好 | 合作周期    | 是  | 一次咨询、短期项目、长期合作，可多选          |
| 需求   | 正在寻找的技能 | 否  | 最多 5 个，用于互补匹配               |

#### 操作

- 发布档案：校验全部必填项；成功提示“人才档案已发布”。
- 保存修改：已发布档案修改立即生效；成功提示“人才档案已更新”。
- 暂停公开：二次确认后状态变为 `Paused`。
- 恢复公开：`Paused` 状态可恢复为 `Published`。
- 用户没有 Live Project 时，在编辑页展示“还没有可展示的项目，上传项目让更多人了解你的实践经历”，点击“上传项目”进入 `/submit`。

### 10.4 发起连接弹窗

| 字段         | 必填 | 规则                             |
| ---------- | -- | ------------------------------ |
| 关联 Project | 否  | 仅可选择发送方拥有的 Live Project；最多 1 个 |
| 合作目的       | 是  | 共同创业、加入项目、短期协作、专业咨询、认识交流、其他    |
| 邀请说明       | 是  | 30-500 字；应说明为什么联系、希望对方参与什么     |
| 分享的微信号      | 条件必填 | 单个微信号；与邮箱至少填写一种；1-64 个字符，去除首尾空格，不允许换行或控制字符 |
| 分享的邮箱       | 条件必填 | 单个邮箱；与微信号至少填写一种；必须符合邮箱格式，最长 254 个字符，去除首尾空格并统一小写 |

发送按钮在请求中置灰，防止重复提交。发送成功后关闭弹窗并提示“连接请求已发送”。

发送方提交请求即表示确认在对方接受后分享本次选择的联系方式。联系方式按连接请求单独授权，不代表同意在人才档案或其他连接中公开。

### 10.5 我的连接

#### 未处理数量提醒

- 顶部导航或用户菜单中的“我的连接”展示当前用户收到且状态为 `Pending` 的请求数量。
- 未处理数量只统计接收方需要处理的 `Pending` 请求，不统计用户发出的 Pending 请求。
- 数量为 0 时不展示数字标记；1-99 显示实际数量；超过 99 显示 `99+`。
- 用户仅打开“我的连接”页面不会减少数量；只有请求成功变为 `Accepted` 或 `Ignored` 后，数量才减 1。
- 收到新请求后数量加 1；重复提交、幂等重试或创建失败不得重复增加。
- 多端或多标签页场景允许通过页面刷新获取最新数量，P0 不要求实时推送。
- 点击数量提醒进入 `/connections`，默认展示“收到的请求”并优先排列 `Pending` 请求。

#### 收到的请求

- 发送方头像、昵称、定位和核心技能。
- 关联 Project 和合作目的。
- 邀请说明、发送时间。
- 查看档案、接受、忽略。
- 点击“接受”后进入联系方式确认弹窗；接收方至少填写并授权一种联系方式，确认后连接才变为 `Accepted`。

#### 发出的请求

- 接收方头像、昵称和定位。
- 关联 Project、合作目的和发送时间。
- 状态：等待回应、已连接、暂未建立连接。
- `Accepted` 状态展示对方授权的微信号或邮箱，并提供复制操作。

#### 联系方式交换规则

- 支持微信号和邮箱，双方各自至少授权一种。
- 发送方在发起连接时必须填写并确认授权；接收方在接受连接时必须填写并确认授权。
- 只有请求变为 `Accepted` 后，系统才同时向双方展示对方授权的信息。
- `Pending` 和 `Ignored` 请求均不得展示对方联系方式。
- 联系方式仅用于该连接双方后续沟通，不展示在公开档案、人才卡片、搜索结果或 Operator 普通列表中。
- Project 的后台联系人信息不得自动作为连接联系方式，用户必须在连接流程中主动填写并授权。

#### 联系方式安全规则

- 联系方式必须在服务端进行字段校验，前端校验只用于即时反馈，不能作为安全边界。
- 联系方式使用服务端管理的密钥加密存储，不以明文写入数据库、缓存、日志、错误信息、审计记录或埋点。
- 联系方式读取接口只允许该 `Accepted` ConnectionRequest 的发送方和接收方访问；其他 User、游客及 Operator 普通后台均返回无权限。
- 返回联系方式前必须同时校验请求状态为 `Accepted`、访问者属于连接双方，并按字段最小化返回。
- Operator 不能在人才管理和连接列表中查看联系方式。若后续因安全事件需要查看，必须另行设计带理由、权限和审计记录的受控流程，不纳入 P0。
- API 响应和页面不得预加载无权查看的联系方式；`Pending` 阶段前端不能仅通过隐藏 UI 保护数据。
- 联系方式不进入搜索索引、SEO 元数据、页面缓存、分析系统或第三方监控上下文。

#### 重复请求规则

- 同一对 User 不论方向同时最多存在 1 条 `Pending` 请求。
- 请求 `Ignored` 后可以立即重新发起；P0 不设置忽略冷却期。
- 任一方向已存在 `Accepted` 请求时，双方视为已连接，不允许再次发送，页面显示“已连接”。
- 用户不能向自己发送连接请求。
- `Cancelled` 请求不能继续处理；如无其他冷却或已连接限制，发送方可重新发起请求。
- 连接请求按北京时间（UTC+8）自然日计算发送上限：`Published` TalentProfile 用户每天最多成功创建 10 条；没有 TalentProfile 或拥有 `Paused` TalentProfile 的已登录用户每天最多成功创建 3 条；拥有 `Suspended` TalentProfile 的用户不能创建请求。

## 11. 匹配规则

### 11.1 原则

- 首版使用确定性规则，不使用不可解释的黑盒 AI。
- 匹配分仅用于排序和辅助判断，不展示为能力评分。
- 大于 0 的匹配分必须附带至少 1 条可读原因；匹配分为 0 时不展示分数，统一归入“暂无明显匹配”。
- 缺失维度按 0 分处理，不用其他维度同比放大，避免资料不全获得虚高分。

### 11.2 计算前提

只有访问者和候选人都拥有 `Published` TalentProfile 时才计算个性化匹配。

### 11.3 评分模型

```text
匹配度 = 共同技能得分 × 25%
       + 互补技能得分 × 35%
       + 项目领域得分 × 25%
       + 合作周期得分 × 15%
```

| 维度   | 计算建议                            | 解释示例              |
| ---- | ------------------------------- | ----------------- |
| 共同技能 | 双方核心技能交集 / 访问者核心技能数，最高 100      | “你们有 3 项共同技能”     |
| 互补技能 | 候选人核心技能命中访问者“正在寻找的技能”的比例，最高 100 | “TA 擅长你正在寻找的全栈开发” |
| 项目领域 | 双方感兴趣品类的重合比例                    | “共同关注开发者工具”       |
| 合作周期 | 双方合作周期选项的兼容项比例                  | “都接受长期合作”         |

分数取整到 0-100。若用户未填写“正在寻找的技能”，互补技能维度为 0，不重新归一化其他维度，并提示完善资料以提升推荐准确度。

### 11.4 原因展示

最多展示 3 条原因，优先级为：互补技能、合作周期、共同领域、共同技能。不得展示“系统认为你们很合适”等不可验证文案。

### 11.5 冷启动

- 无 TalentProfile：不计算匹配，按最新加入展示。
- 没有 TalentProfile：不使用未发布的页面输入参与匹配。
- 新发布档案：允许立即进入列表，不因缺少行为数据降低曝光。
- 候选不足：展示当前筛选条件下的全部结果，不自动放宽用户显式选择的技能、角色等条件。

## 12. 权限、隐私与安全

### 12.1 权限矩阵

| 能力        | 游客 | 登录用户           | 档案本人      | Operator |
| --------- | -- | -------------- | --------- | -------- |
| 浏览广场和公开档案 | 是  | 是              | 是         | 是        |
| 查看个性化匹配   | 否  | 需 Published 档案 | 是         | 否        |
| 创建和编辑档案   | 否  | 是              | 是         | 否        |
| 发起连接      | 否  | 需登录；若有 TalentProfile 则不得为 Suspended | 是，但不能连接自己 | 否        |
| 处理收到的请求   | 否  | 需 Published 或 Paused | 是         | 否        |
| 暂停自己的档案   | 否  | 否              | 是         | 否        |
| 下架违规档案    | 否  | 否              | 否         | 是        |

### 12.2 隐私规则

- 默认只展示用户主动发布的资料。
- 不公开精确位置、生日、登录 IP 和精确在线状态；联系方式只在连接变为 `Accepted` 后按本次授权向对方展示。
- Project 中的后台联系人信息不得被人才档案读取或展示。
- 双方只交换在本次连接中主动填写并确认的联系方式，未授权的私人信息不得展示。
- 用户暂停或被下架后，立即从公开列表、搜索和匹配结果移除。
- P0 不提供 TalentProfile 自助删除。用户暂停档案后不再公开展示；如需永久删除人才档案、连接记录或授权联系方式，通过联系运营处理。

### 12.3 风控规则

- 先发后审：发布和修改成功后立即公开，不提供自动内容审核；发现违规内容时由 Operator 通过联系运营和日常巡检处理。
- 连接请求按发送方当前档案状态和北京时间（UTC+8）自然日计算发送上限：拥有 `Published` TalentProfile 的用户每天最多成功创建 10 条；其他已登录用户每天最多成功创建 3 条；拥有 `Paused` TalentProfile 的用户按普通登录用户上限计算，每天最多 3 条；拥有 `Suspended` TalentProfile 的用户不能创建连接请求。校验失败和幂等重试不计数，达到上限后提示次日再试。
- 不提供站内举报按钮或举报表单；用户发现虚假资料、骚扰、广告、侵权或其他问题时，通过“联系运营”入口反馈。
- Operator 下架必须填写原因并记录操作人和时间。
- `Suspended` 为终态，用户不能发起或处理连接请求；页面显示下架原因并提示联系运营。

## 14. 非功能要求

- 响应式支持 320px 以上移动端和桌面端。
- 人才广场首屏在正常网络下应有明确加载反馈，列表接口 P95 建议低于 800ms。
- 搜索和筛选参数可通过 URL 恢复。
- 公开档案支持 SEO title、description 和分享卡片；暂停或下架档案应为 `noindex`。
- 交互控件支持键盘操作、可见焦点和屏幕阅读器标签。
- 头像加载失败使用昵称首字母占位，不影响主要内容阅读。
- 所有连接状态变更必须具备幂等保护，避免重复请求导致状态异常。

## 15. 验收标准

### 15.1 人才档案

- 登录用户填写资料并满足规则后可直接发布；不创建 Draft，也不支持保存草稿。
- 未满足必填规则时不能发布，并定位到第一个错误字段。
- Published 档案可在广场被搜索，Paused 和 Suspended 档案不可被搜索。
- 人才档案不要求用户具有 Founder 角色。
- 档案不提供技能熟练度或技能证据字段，也不展示技能排名。
- 公开档案自动展示用户的 Live Project；没有 Live Project 时，本人可以看到上传项目引导并进入 `/submit`。
- 公开页面不展示任何后台联系方式。

### 15.2 搜索与匹配

- 搜索、筛选、排序和分页可以组合使用，刷新页面后状态不丢失。
- 不同筛选项按 AND、同一多选项按 OR 执行。
- 只有双方均有 Published 档案时展示个性化匹配分。
- 大于 0 的匹配分与规则输入一致，并至少展示 1 条具体原因；匹配分为 0 时不展示分数，统一归入“暂无明显匹配”。
- 不满足计算条件时不展示伪造或默认匹配分。

### 15.3 连接请求

- 游客点击连接后进入登录流程，返回后恢复连接表单但不自动发送。
- 已登录用户可以发送请求；没有 TalentProfile 的用户不参与匹配计算。拥有 TalentProfile 且状态为 `Suspended` 的用户不能发送请求。
- 不能向自己发送请求，不能产生两条并行 Pending 请求。
- 接收方可接受或忽略 Pending 请求；P0 不支持发送方撤回请求。档案被 Suspended 时，相关 Pending 自动转为 Cancelled，双方不能继续处理。
- “我的连接”未处理数量等于当前用户作为接收方的 Pending 请求数；处理成功后数量同步减少。
- 数量为 0 时隐藏，超过 99 时显示 `99+`；仅打开列表不改变数量。
- 发送方发起请求时必须确认至少一种联系方式，接收方接受请求时也必须确认至少一种联系方式；只有状态变为 Accepted 后才能互相查看。
- Pending、Ignored 和 Cancelled 状态不得泄露任一方联系方式。
- Paused 用户不能接收新请求，但仍可作为发送方发起请求，也可以处理暂停前已有 Pending；Suspended 用户不能发送或处理请求，且其 Pending 不计入未处理数量。
- Paused 和 Suspended 用户已有 Accepted 连接及联系方式继续可见。
- 接受和忽略操作具备幂等性；重复 API 调用返回现有状态，不修改首次处理时间、联系方式或产生额外记录。
- 忽略后可立即重发；北京时间自然日内的分层发送上限（Published TalentProfile 用户最多 10 条，其他已登录用户最多 3 条，Suspended 用户为 0 条），以及 Suspended 限制正确生效。

### 15.4 Operator 与隐私

- Operator 可搜索人才档案并填写原因后下架。
- 下架操作有可查询的操作记录。
- Suspended 档案立即从公开列表和详情移除，状态不可恢复；本人看到下架原因和联系运营提示。
- Paused 仍可处理暂停前已有 Pending 请求，Suspended 不可处理；Suspended 相关 Pending 不计入未处理数量。
- Paused 和 Suspended 均保留已有 Accepted 连接及双方授权的联系方式。
- 联系方式格式校验、加密存储、连接双方访问控制及日志脱敏符合本文安全规则。
- 埋点不包含邀请正文、联系方式等敏感字段。

## 16. 上线策略

1. 内部测试：使用测试档案验证筛选、匹配和完整连接状态机。
2. 小范围邀请：邀请一批具有完整 Project 经历的 Founder 和贡献者建立档案，解决冷启动。
3. 灰度开放：仅对登录用户展示入口，游客可通过直链浏览。
4. 全量开放：导航公开入口，持续观察联系运营反馈量、请求接受率和发送频控命中率。
5. 上线两周后复盘：评估漏斗、低质量邀请、技能词库缺口和匹配原因可信度。

## 17. 风险与应对

| 风险              | 影响          | 应对                                |
| --------------- | ----------- | --------------------------------- |
| 人才数量不足          | 列表空、匹配价值低   | 上线前定向邀请种子用户，鼓励用户上传 Project 展示实践经历 |
| 自填技能可信度低        | 匹配质量和信任下降   | 明示技能为用户自述，并优先展示用户的 Live Project   |
| 连接请求骚扰          | 用户流失和投诉     | Published TalentProfile 用户每日 10 条、其他登录用户每日 3 条的分层频控、忽略、联系运营和下架 |
| 匹配分被误解          | 用户将分数视作能力评价 | 文案统一为“合作匹配”，展示原因，不做人才排行           |
| 与现有 Follow 语义冲突 | 数据和产品行为不一致  | P0 不实现人才关注；后续单独决策是否扩展 Follow 目标   |
| 外部 User 资料不可写   | 档案编辑体验割裂    | 清晰区分统一账号资料与人才档案资料，提供跳转入口          |
