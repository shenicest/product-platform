# 0017. 命题详情字段落在 `challenges` 上，版本记录只留痕不留快照

## Status

Accepted

## Context

命题详情页要展示「命题卡」正文（背景 / 范围 / 不做什么 / 一个月最小成果 / 建议技能 /
团队容量 / 负责人 / 响应时限）、「评分与奖励」（五维权重、单次上限、赛季口径）与
「公开与权益」（七项条款），还要在右栏给出「版本记录」。

现状里 `challenges` 只有五件套 + 类型 / 主题 / 企业 / 容量，其余内容无处安放；
`challenge_resources` 存的是主办方逐条跟踪的兑现清单，不是命题正文。

有两种做法：

- **A. 把命题卡正文塞进 `realProblem` 之类的现有长文本字段**，或新增一张
  `challenge_details` 一对一表。
- **B. 直接给 `challenges` 加列**，版本记录用一张只写「第几版 / 谁 / 为什么 / 何时」的
  `challenge_versions` 表。

A 的问题：塞进现有字段会让「真实问题」在详情页、后台表格、发布门槛校验里承担三种语义，
五件套的判定立刻变得不可解释；另开一对一表则让每次读命题都要多一次 join 或一次额外查询，
而命题本身没有「详情可以不存在」的场景。

## Decision

1. **命题详情字段直接加在 `challenges` 上**，全部可空、**都不参与发布门槛** ——
   发布仍然只看五件套（`CHALLENGE_INCOMPLETE`）。
2. **七项权益分列存**（`rights_*` 七列），不合并成一段自由文本：合成一段必然让某一项
   在公开页里消失，而「先明示再签」要求每一项都能被单独引用。
3. **`challenge_versions` 只留痕，不做快照**：正文永远只有 `challenges` 里那一份，
   历史内容查 `audit_logs` 的变更明细。与「发布后编辑使 version +1，不做版本快照」
   的既有口径一致，也避免一份正文存 N 份。
4. **五维权重不落默认值**：`scoring_weights` 为 NULL 表示「未配置，按等权」，
   把默认权重写进每一行会让「没配过」和「配成默认值」无法区分。写入时合计必须为 100。
5. **关注独立建表** `challenge_follows`，与关注 Founder 的 `follows` 无关；
   关注数按需 COUNT，不加冗余字段（沿用 ADR-0008）。
6. **赛季项目阶段 `stage` 加在 `season_projects` 上**（不是 `projects`）：阶段是
   「这个项目在这个赛季走到哪一步」，同一个项目换赛季重新从 seed 起算。

## Consequences

- `GET /challenges/:id` 一次查询即可拿全命题正文，不需要额外 join。
- 主办方后台的「编辑详情」表单与详情页展示共用同一份字段，两处不会漂移。
- 结果与证据（R0—R6）与命题报告本批不做，只留占位；后续加表时不需要改 `challenges`。
- 权益七列是横向扩张：再加第八项条款要改表。接受这个代价 —— 条款项是产品口径，
  变动频率远低于正文。
